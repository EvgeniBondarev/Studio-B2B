🏗️ Архитектура Multi-Tenant SaaS

Полная схема модулей и связей для системы управления заказами

📚 Key Concepts & Definitions

🏢 B2B SaaS Multi-Tenant

Business-to-Business Software as a Service architecture where multiple organizations (tenants) share the same application infrastructure while maintaining complete data isolation through separate databases per tenant.

B2B-программа как услуга с мульти-тенантной архитектурой, где несколько организаций (тенантов) используют одно приложение, но с полной изоляцией данных через отдельные базы данных для каждого клиента.

🔐 Permission-Based Authorization

Dynamic access control system where permissions (atomic actions) are assigned to roles, and roles are assigned to users. Unlike static role-based systems, permissions can be combined flexibly at runtime.

Динамическая система контроля доступа, где права (атомарные действия) назначаются ролям, а роли — пользователям. В отличие от статичных ролевых систем, права могут гибко комбинироваться во время выполнения.

🔄 CQRS with MediatR

Command Query Responsibility Segregation pattern separating read (queries) and write (commands) operations. MediatR acts as a mediator implementing the mediator pattern for in-process messaging.

Разделение ответственности команд и запросов (CQRS) с паттерном "Посредник". MediatR реализует обмен сообщениями внутри процесса, разделяя операции чтения и записи.

🏛️ Clean Architecture

Architectural pattern with dependency inversion, where business logic is independent of frameworks and UI. Dependencies flow inward: Presentation → Application → Domain → Infrastructure.

Архитектурный паттерн с инверсией зависимостей, где бизнес-логика не зависит от фреймворков и UI. Зависимости направлены внутрь: Представление → Приложение → Домен → Инфраструктура.

📦 Vertical Slice Architecture

Organizing code by features instead of layers. Each feature contains its own controllers, services, and data access, making the codebase more maintainable and reducing coupling.

Организация кода по функциям вместо слоев. Каждая функция содержит свои контроллеры, сервисы и доступ к данным, что делает код более поддерживаемым и уменьшает связанность.

🗃️ Domain-Driven Design (DDD)

Approach to software development focusing on the core domain and domain logic. Uses rich domain models, value objects, aggregates, and ubiquitous language to solve complex business problems.

Подход к разработке ПО, сфокусированный на основной предметной области и бизнес-логике. Использует богатые доменные модели, объекты-значения, агрегаты и единый язык для решения сложных бизнес-задач.

🔄 Transaction Engine

Dynamic system that executes business transactions based on configurable definitions. Allows users to create custom transaction types with forms, validation rules, and external system integrations.

Динамическая система выполнения бизнес-транзакций на основе настраиваемых определений. Позволяет пользователям создавать кастомные типы транзакций с формами, правилами валидации и интеграциями с внешними системами.

🔌 Outbox Pattern

Reliability pattern for ensuring event publishing. Events are stored in an outbox table within the same transaction, then a separate process publishes them to external systems, preventing data loss.

Паттерн надежности для гарантированной публикации событий. События сохраняются в таблице outbox в той же транзакции, затем отдельный процесс публикует их во внешние системы, предотвращая потерю данных.

🎯 Row-Level Security

Data access control mechanism that restricts data access at the row level based on user identity or roles. In multi-tenant systems, ensures users can only access data belonging to their tenant.

Механизм контроля доступа к данным на уровне строк на основе идентификации пользователя или ролей. В мульти-тенантных системах обеспечивает доступ пользователей только к данным их тенанта.

🔄 Event Sourcing

Pattern where state changes are recorded as a sequence of events. Instead of storing current state, all events are stored, allowing reconstruction of state at any point in time.

Паттерн, где изменения состояния записываются как последовательность событий. Вместо хранения текущего состояния сохраняются все события, позволяя восстановить состояние в любой момент времени.

TenantMiddleware
Извлекает subdomain из URL (client1.mysaas.com → "client1") и определяет TenantId из Master DB. Реализует стратегию определения тенанта с кэшированием для производительности.
Permission-Based Authorization
Динамическая система проверки прав с использованием ASP.NET Core Identity и RoleClaims. Валидирует права пользователей во время выполнения на основе настраиваемых маппингов роль-право в базе тенанта.
EF Core Tenant Context
Динамически переключается между базами данных в зависимости от TenantId. Использует фабричный паттерн для создания экземпляров DbContext с tenant-specific строками подключения для полной изоляции данных.
Command Handlers (CQRS)
Обрабатывают операции записи (Create, Update, Delete) с использованием MediatR. Реализуют валидацию бизнес-логики, публикацию доменных событий и управление транзакциями с паттерном Unit of Work.
Query Handlers (CQRS)
Обрабатывают операции чтения с оптимизированными паттернами доступа к данным. Реализуют стратегии кэширования, пагинацию и фильтрацию для эффективного извлечения данных из баз тенантов.
Domain Entities
Богатые доменные модели, содержащие бизнес-логику и правила валидации. Реализуют DDD паттерны: агрегаты, объекты-значения и доменные события для инкапсуляции бизнес-поведения.
Hangfire Background Jobs
Надежная обработка фоновых задач с изоляцией по тенантам. Использует отдельные очереди для каждого тенанта и автоматические повторы для интеграций с внешними API, синхронизации с 1С и задач обработки данных.
Redis Distributed Cache
Высокопроизводительный слой кэширования с изоляцией по тенантам. Хранит часто используемые данные, сессии пользователей и состояние приложения с настраиваемым TTL и стратегиями инвалидации кэша.
1C Integration Service
RESTful API клиент для интеграции с 1С:Предприятие. Реализует создание документов (ПоступлениеТоваров, ПеремещениеТоваров), синхронизацию статусов и обработку ошибок с механизмами повтора и outbox паттерном.
Marketplace Adapters
Унифицированный интерфейс для интеграций с несколькими маркетплейсами (Ozon, Wildberries, Yandex Market). Реализует маппинг статусов, pipeline обогащения заказов и стандартизированные модели данных с использованием паттерна адаптер.

Marketplace Integration Flow
Automated order synchronization from external marketplaces using adapter pattern. Handles status mapping, deduplication, and order enrichment with background job processing and caching optimization.
Автоматизированная синхронизация заказов из внешних маркетплейсов с использованием паттерна адаптер. Обрабатывает маппинг статусов, дедупликацию и обогащение заказов с фоновыми задачами и оптимизацией кэширования.
Process: Hangfire Job → Marketplace API → Adapter → StatusResolver → Database
Components: ImportOrdersJob, OzonAdapter, StatusResolver, OrderEnricher
Features: Deduplication, status mapping, error handling, retry logic
Status Mapping Strategy
Dynamic status resolution with fallback strategy. Uses tenant-specific mappings first, then global defaults, with Redis caching for performance optimization and automatic cache invalidation on changes.
Динамическое разрешение статусов со стратегией fallback. Использует tenant-specific маппинги первыми, затем глобальные значения по умолчанию, с Redis кэшированием для оптимизации производительности и автоматической инвалидацией кэша при изменениях.
Cache Strategy: status_map:{tenantId}:{marketplace}:{externalStatus}
Fallback Order: Tenant → Global → Error
TTL: 1 hour with manual invalidation
Performance: >95% cache hit ratio for frequently used statuses
Order Deduplication Logic
Prevents duplicate order creation using composite unique key (ExternalId + Marketplace). Updates existing orders with new data while preserving audit trail and status history.
Предотвращает создание дубликатов заказов с использованием составного уникального ключа (ExternalId + Marketplace). Обновляет существующие заказы новыми данными, сохраняя аудит и историю статусов.
Check Logic: SELECT WHERE ExternalId='12345' AND Marketplace='Ozon'
Update Strategy: Merge new data, preserve creation date, update status
Audit Trail: Track all changes with timestamps and source
Order Enrichment Pipeline
Data enrichment process for imported orders. Adds customer details, product information, and calculated fields. Validates data completeness and applies business rules for order processing.
Процесс обогащения данных для импортированных заказов. Добавляет детали клиентов, информацию о продуктах и вычисляемые поля. Валидирует полноту данных и применяет бизнес-правила для обработки заказов.
Enrichment Steps: Customer lookup → Product validation → Price calculation → Tax computation
Validation Rules: Required fields, business constraints, data format checks
Output: Complete order ready for processing
Order Entity Flow
State machine pattern for order lifecycle management. Each status transition is validated through transaction definitions with business rules enforcement and audit trail maintenance.
Паттерн конечного автомата для управления жизненным циклом заказа. Каждый переход статуса валидируется через определения транзакций с принуждением бизнес-правил и поддержкой аудита.
Step 1: Created → Status: "New"
Step 2: Transaction Started → Status: "Processing"
Step 3: 1C Document Created → Status: "Ordered"
Step 4: Goods Received → Status: "Received"
Database Switching Logic
Multi-tenant data access strategy using context switching. Master database stores tenant metadata and connection strings, while tenant databases contain isolated business data with separate connection pools.
Стратегия доступа к данным в мульти-тенантной среде с использованием переключения контекста. Master база хранит метаданные тенантов и строки подключения, в то время как tenant базы содержат изолированные бизнес-данные с отдельными пулами соединений.
Master DB (mysaas_master): Tenants, Users, Billing
Tenant DB (romashka_orders): Orders, Transactions, AspNetUsers
Context Switch: Based on TenantId from subdomain
Tenant Seeding Process
Automated database initialization for new tenants. Idempotent seeding process creates default statuses, transaction types, roles, and permissions ensuring immediate system usability after registration.
Автоматизированная инициализация базы данных для новых тенантов. Идемпотентный процесс наполнения создает статусы по умолчанию, типы транзакций, роли и права, обеспечивая немедленную пригодность системы к использованию после регистрации.
Seed Components: Order Statuses, Transaction Definitions, Roles & Permissions, Default Settings
Process: Create DB → Apply Migrations → Run Seeder → Create Admin User
Idempotency: Safe to run multiple times without data duplication
JWT Token Generation
Secure authentication token creation with tenant context. Contains user identity, tenant information, and permission claims for stateless API authentication with configurable expiration.
Создание безопасного токена аутентификации с контекстом тенанта. Содержит идентификацию пользователя, информацию о тенанте и claims прав для stateless аутентификации API с настраиваемым сроком действия.
Claims: {sub=user-456, tenant=guid-123, permissions=["Orders.Create", "Orders.View", "Transactions.Execute"]}
Expiration: 1 hour (configurable)
Signing: RSA private key with certificate validation
Permission Validation Flow
Runtime authorization check using cached permission data. Validates user access to specific operations with role-based permission resolution and caching for high-performance authorization decisions.
Проверка авторизации во время выполнения с использованием кэшированных данных прав. Валидирует доступ пользователя к конкретным операциям с разрешением прав на основе ролей и кэшированием для высокопроизводительных решений авторизации.
Process: Extract permissions from JWT → Cache lookup → Role resolution → Permission validation
Cache Key: permissions:user-456
Cache TTL: 1 hour with invalidation on role changes

Production Deployment Architecture
Корпоративная стратегия развертывания с высокой доступностью и масштабируемостью. Реализует балансировку нагрузки, шардинг баз данных, кэширующие кластеры и комплексный мониторинг для production нагрузок.
Окружение: Production on-premise или облако (AWS/Azure)
Балансировка нагрузки: Nginx с SSL termination и health checks
Масштабирование приложения: 2+ экземпляра ASP.NET Core за балансировщиком
Масштабирование БД: Отдельные экземпляры SQL Server на группу тенантов
Стратегия кэширования: Redis Master-Slave для высокой доступности
Фоновая обработка: Hangfire с постоянным хранилищем
Мониторинг: Prometheus + Grafana + ELK stack
Request Flow Summary
Полный жизненный цикл запроса от браузера пользователя до ответа базы данных. Демонстрирует определение тенанта, аутентификацию, авторизацию, выполнение бизнес-логики и сохранение данных с оптимизацией производительности.
1. Запрос пользователя: https://romashka.mysaas.com/api/orders
2. Разрешение DNS: romashka.mysaas.com → 192.168.1.5 (Nginx)
3. Балансировщик: Nginx → Экземпляр ASP.NET Core (10.0.1.100)
4. Определение тенанта: Middleware извлекает "romashka" → TenantId=guid-123
5. Аутентификация: JWT валидация → Права пользователя из кэша
6. Авторизация: Проверка права "Orders.View"
7. Бизнес-логика: Command Handler → Domain Entity → Database
8. Доступ к БД: TenantDbContext(romashka_orders) → SQL Server
9. Ответ: Данные заказа → JSON ответ → Браузер пользователя

Критичные метрики производительности и соглашения об уровне обслуживания для production системы. Определяет цели по времени ответа, лимиты использования ресурсов и требования доступности для корпоративного развертывания.
Время ответа: < 200мс для API вызовов

Security Layers
Комплексная реализация безопасности на всех уровнях системы. Реализует сетевую безопасность, безопасность приложений, защиту данных, аутентификацию, авторизацию и меры соответствия для корпоративных требований.
Сетевая безопасность: Firewall, DDoS защита, VPN доступ
Безопасность приложений: JWT токены, HTTPS везде, CORS
Защита данных: Шифрование БД, изоляция тенантов, аудит логи
Аутентификация: Многофакторная аутентификация, политики паролей, управление сессиями
Авторизация: Ролевой доступ, система прав, безопасность на уровне данных
Соответствие: GDPR, хранение данных, шифрование резервных копий
Scalability Strategy
Многомерный подход к масштабированию для обработки роста. Реализует горизонтальное масштабирование серверов приложений, шардинг баз данных для данных тенантов и распределенное кэширование для оптимизации производительности.
Масштабирование приложения: Балансировщик + множество экземпляров
Масштабирование БД: База данных на тенанта или шардинг БД
Масштабирование кэша: Redis кластер с consistent hashing
Масштабирование фоновых задач: Несколько серверов Hangfire
Масштабирование мониторинга: Распределенный сбор метрик
Disaster Recovery
Планирование непрерывности бизнеса с процедурами резервного копирования и восстановления. Реализует автоматизированные резервные копии, географическую избыточность и цели времени восстановления для корпоративной надежности.
Стратегия резервирования: Полные резервные копии ежедневно + логи транзакций ежечасно
Цель времени восстановления (RTO): 4 часа
Цель точки восстановления (RPO): 1 час
Географическая избыточность: Кросс-региональная репликация
Тестирование: Ежемесячные учения по восстановлению после сбоя
