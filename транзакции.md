**Пример:**
*   **Имя:** "Заказ поставщику".
*   **Суть:** Менеджер нажимает кнопку -> Открывается форма (выбор поставщика, дата поставки) -> Менеджер жмет "Провести" -> Статус заказа меняется на "Заказан" -> В 1С создается документ "Заказ поставщику".

Чтобы реализовать **гибкий конструктор**, где пользователь сам настраивает, какие поля заполнять и какой документ 1С создавать, нужно разделить архитектуру на **Определение (Definition)** и **Исполнение (Execution)**.

Вот реализация на основе твоих схем (8, 9, 10).

### 1. База Данных: Мета-модель Конструктора (Schema Design)

Нам нужны две основные таблицы: одна описывает **правила** (шаблон), вторая хранит **историю** (конкретные операции).

#### А. Шаблон Транзакции (TransactionDefinition)
Это настройки из "Конструктора". Хранится в базе.

```csharp
public class TransactionDefinition
{
    public Guid Id { get; set; }
    public Guid TenantId { get; set; }
    
    public string Name { get; set; } // "Заказ поставщику"
    
    // Логика переходов (Схема 9: Начальный/Конечный статус)
    public int FromStatusId { get; set; } 
    public int ToStatusId { get; set; }

    // 1. КОНСТРУКТОР ФОРМЫ (Какие поля показать менеджеру?)
    // Храним JSON-схему полей: 
    // [
    //   { "Key": "SupplierId", "Type": "Select", "Source": "Suppliers", "Label": "Выберите поставщика" },
    //   { "Key": "DeliveryDate", "Type": "Date", "Required": true, "Label": "Дата поставки" }
    // ]
    public string FormSchemaJson { get; set; }

    // 2. МАППИНГ (Как эти поля влияют на заказ?)
    // { "SupplierId": "Order.SupplierId", "DeliveryDate": "Order.ExpectedDate" }
    public string FieldMappingJson { get; set; }

    // 3. НАСТРОЙКИ 1С (Схема 10: Данные 1С)
    // Какой тип документа создавать в 1С?
    public string OneCDocumentType { get; set; } // "PurchaseOrder", "Shipment", etc.
}
```

#### Б. Журнал Транзакций (TransactionRecord)
Это история. "Кто, когда и что сделал". (Схема 9).

```csharp
public class TransactionRecord
```

### 2. Логика Исполнения (Transaction Engine)

Это сервис, который "проводит" транзакцию. Он работает динамически, читая настройки из БД.

```csharp
public class TransactionService
{
    private readonly TenantDbContext _db;
    private readonly IBackgroundJobClient _hangfire; // Для 1С

    public async Task<Result<Guid>> ExecuteTransactionAsync(Guid orderId, Guid definitionId, Dictionary<string, object> inputData)
    {
        // 1. Загружаем шаблон и заказ
        var def = await _db.TransactionDefinitions.FindAsync(definitionId);
        var order = await _db.Orders.FindAsync(orderId);

        // 2. Валидация (Подходит ли статус?)
        if (order.StatusId != def.FromStatusId)
            return Result.Failure("Статус заказа не подходит для этой операции");

        // 3. Создаем запись в истории (Журнал)
        var record = new TransactionRecord
        {
            Id = Guid.NewGuid(),
            OrderId = orderId,
            DefinitionId = definitionId,
            CreatedAt = DateTime.UtcNow,
            InputDataJson = JsonSerializer.Serialize(inputData),
            OneCStatus = OneCSyncStatus.Pending
        };
        _db.TransactionRecords.Add(record);

        // 4. ПРИМЕНЕНИЕ ИЗМЕНЕНИЙ К ЗАКАЗУ (Reflection / Dynamic)
        // Читаем маппинг из шаблона: "Поле формы -> Поле заказа"
        var mappings = JsonSerializer.Deserialize<Dictionary<string, string>>(def.FieldMappingJson);
        
        foreach (var map in mappings)
        {
            var inputValue = inputData[map.Key]; // То, что ввел юзер
            var orderProp = map.Value; // Имя поля в Order (например "SupplierId")
            
            // Используем FastMember или Reflection для установки значения
            SetProperty(order, orderProp, inputValue);
        }

        // 5. Смена статуса заказа
        order.StatusId = def.ToStatusId;
        record.IsAppliedToOrder = true;

        await _db.SaveChangesAsync();

        // 6. ОТПРАВКА В 1С (Асинхронно!)
        // Мы передаем ID записи журнала, чтобы потом обновить в ней статус 1С
        _hangfire.Enqueue<OneCJob>(job => 
            job.SendTransactionTo1C(record.Id, def.OneCDocumentType));

        return Result.Success(record.Id);
    }

    private void SetProperty(object target, string propName, object value)
    {
        // Упрощенная логика рефлексии
        var prop = target.GetType().GetProperty(propName);
        // Тут нужна конвертация типов (string -> Guid, string -> DateTime)
        var convertedValue = Convert.ChangeType(value, prop.PropertyType);
        prop.SetValue(target, convertedValue);
    }
}
```

### 3. Интеграция с 1С (Гибкая)

Твой джоб (OneCJob) должен уметь собирать разные JSON для 1С в зависимости от типа транзакции.

```csharp
public class OneCJob
{
    public async Task SendTransactionTo1C(Guid recordId, string docType)
    {
        var record = await _db.TransactionRecords
            .Include(x => x.Order)
            .FirstOrDefaultAsync(x => x.Id == recordId);
            
        var inputData = JsonSerializer.Deserialize<JsonNode>(record.InputDataJson);

        object payload = null;

        // Фабрика пейлоадов для 1С в зависимости от типа документа
        switch (docType)
        {
            case "OrderToSupplier":
                payload = new 
                {
                    OrderId = record.Order.ExternalId,
                    Supplier = inputData["SupplierId"].ToString(), // Данные из формы
                    Date = inputData["DeliveryDate"],
                    Items = record.Order.Items.Select(x => new { x.Sku, x.Qty })
                };
                break;
                
            case "Shipment":
                payload = new { /* Структура для отгрузки */ };
                break;
        }

        try 
        {
            // Отправка (используем твой OneCApiClient)
            var response = await _apiClient.PostAsync(docType, payload);
            
            // Обновляем историю
            record.OneCStatus = OneCSyncStatus.Success;
            record.OneCId = response.ExternalId;
        }
        catch (Exception ex)
        {
            record.OneCStatus = OneCSyncStatus.Error;
            record.OneCError = ex.Message;
        }
        
        await _db.SaveChangesAsync();
    }
}
```

### 4. UI: Как строится страница (Frontend)

Это самое крутое для пользователя. Страница не захардкожена.

1.  **GET /api/transactions/definitions/{orderId}**: Фронт спрашивает: "Какие кнопки мне показать для этого заказа?"
    *   Бэкенд смотрит текущий статус заказа.
    *   Находит в `TransactionDefinitions` все правила, где `FromStatus == CurrentStatus`.
    *   Возвращает список кнопок: `[{ Id: "...", Name: "Заказ поставщику" }, { Id: "...", Name: "Отмена" }]`.

2.  **Пользователь жмет "Заказ поставщику"**:
    *   Фронт получает `FormSchemaJson` этого определения.
    *   **Рендерит форму на лету**:
        *   Видит `Type: Select, Source: Suppliers` -> грузит список поставщиков, рисует Dropdown.
        *   Видит `Type: Date` -> рисует DatePicker.

3.  **POST /api/transactions/execute**:
    *   Фронт отправляет введенные данные.

### Резюме по Схемам

*   **Схема 9 (Транзакция):**
    *   `Описание`, `Настройки` -> это `TransactionDefinition`.
    *   `Данные 1С` -> это поля `OneCId`, `OneCStatus` в `TransactionRecord`.
    *   `Начальный/Конечный статус` -> поля в `TransactionDefinition`.
*   **Схема 10 (Настройки транзакции):**
    *   `Поля для изменения` -> это `FieldMappingJson` (маппинг ввода юзера на поля заказа).
    *   `Правила вычисления` -> можно добавить поле `CalculationScript`, если нужно считать суммы динамически.

Такая архитектура позволяет тебе (или админу клиента) через UI создать новую операцию "Срочная доставка", добавить поле "Курьер", настроить смену статуса и отправку в 1С — **без изменения кода C#**.
 Если **Транзакция** — это документ (действие), то **Пайплайн (Pipeline)** — это "труба", через которую проходит этот документ, чтобы изменить состояние системы.

В ERP-системах смена статуса — это не просто `Order.Status = NewStatus`. Это сложный процесс валидации, проведения по регистрам и финализации.

Вот как спроектировать этот механизм.

### 1. Модель данных: Граф переходов (Workflow Graph)

Сначала нужно определить правила игры: из какого статуса в какой можно переходить. В SaaS это должно настраиваться (Схема 14).

**Таблица `StatusTransitions` (Правила переходов):**
Позволяет настроить "защиту от дурака" (нельзя из "Нового" сразу сделать "Возврат").

```csharp
public class StatusTransition

    public Guid AllowedDefinitionId { get; set; }
```

### 2. Архитектура Пайплайна (Chain of Responsibility)

Когда пользователь нажимает "Провести транзакцию", запускается конвейер. Каждый шаг — это изолированный класс.

#### Интерфейс шага:
```csharp
public interface ITransitionStep
{

    // context - мешок с данными (Заказ, Транзакция, Пользователь, Настройки)
    Task<Result> ExecuteAsync(TransitionContext context, Func<Task<Result>> next);
}
```

```csharp
public class TransitionContext
{
    public Order Order { get; set; }
    public TransactionRecord Transaction { get; set; }
    public TransactionDefinition Definition { get; set; }
    public TenantDbContext Db { get; set; }
    // ... дополнительные данные
}
```

### 3. Реализация шагов Пайплайна

Давай соберем цепочку, которая покрывает твои схемы (1С, Склады, Транзакции).

#### Шаг 1: Валидация перехода (Guard Step)
Проверяет, разрешен ли такой переход в таблице `StatusTransitions` и выполнены ли условия.

```csharp
public class ValidateTransitionStep : ITransitionStep
{
    public async Task<Result> ExecuteAsync(TransitionContext ctx, Func<Task<Result>> next)
    {
        // 1. Ищем разрешение в графе переходов
        var rule = await ctx.Db.StatusTransitions
            .FirstOrDefaultAsync(x => 
                x.FromStatusId == ctx.Order.StatusId && 
                x.ToStatusId == ctx.Definition.ToStatusId);

        if (rule == null)
            return Result.Failure($"Переход из '{ctx.Order.Status}' в этот статус невозможен.");

        // 2. Проверяем бизнес-правила (например, заполнены ли обязательные поля)
        var rules = JsonSerializer.Deserialize<ValidationRules>(rule.ValidationRulesJson);
        if (rules.RequireStockCheck)
        {
             // Логика проверки остатков...
        }

        return await next();
    }
}
```

#### Шаг 2: Финансовые и Складские движения (Ledger Step)
Здесь работает твой "Конструктор проводок".

```csharp
public class ApplyLedgerStep : ITransitionStep
{
    public async Task<Result> ExecuteAsync(TransitionContext ctx, Func<Task<Result>> next)
    {
        // Если транзакция требует списания товаров
        if (ctx.Definition.StockAction == StockActionType.Decrease)
        {
            // Списываем со склада
            foreach (var item in ctx.Transaction.Items)
            {
                var stock = await ctx.Db.Stocks.Find(item.ProductId, ctx.Transaction.WarehouseId);
                stock.Quantity -= item.Quantity;
            }
        }
        
        // Если транзакция создает долг клиенту (Финансы)
        if (ctx.Definition.FinanceAction == FinanceActionType.CreateDebt)
        {
            ctx.Db.BalanceHistory.Add(new BalanceRecord { ... });
        }

        return await next();
    }
}
```

#### Шаг 3: Фиксация и смена статуса (Commit Step)
```csharp
public class CommitStatusStep : ITransitionStep
{
    public async Task<Result> ExecuteAsync(TransitionContext ctx, Func<Task<Result>> next)
    {
        // Меняем статус заказа
        ctx.Order.StatusId = ctx.Definition.ToStatusId;
        ctx.Order.UpdatedAt = DateTime.UtcNow;
        
        // Помечаем транзакцию как проведенную
        ctx.Transaction.IsApplied = true;

        await ctx.Db.SaveChangesAsync(); // Физическая запись в БД

        return await next();
    }
}
```

#### Шаг 4: Пост-процессинг (1С, SignalR)
Этот шаг выполняется **после** того, как данные сохранены (даже если он упадет, заказ уже изменен).

```csharp
public class PostProcessingStep : ITransitionStep
{
    private readonly IBackgroundJobClient _hangfire;

    public async Task<Result> ExecuteAsync(TransitionContext ctx, Func<Task<Result>> next)
    {
        // 1. Отправка в 1С (Асинхронно через Hangfire)
        if (!string.IsNullOrEmpty(ctx.Definition.OneCDocumentType))
        {
            _hangfire.Enqueue<OneCJob>(j => 
                j.SendTransactionTo1C(ctx.Transaction.Id, ctx.Definition.OneCDocumentType));
        }

        // 2. Уведомление через SignalR
        _hangfire.Enqueue<NotificationJob>(j => 
            j.NotifyUser(ctx.Order.UserId, "Статус заказа изменен"));

        return await next();
    }
}
```

### 4. Конечный статус и "Заморозка" (Final State)

В Схеме статусов (14) есть конечные точки (Зеленые/Красные блоки), например "Выполнен" или "Отменен".

**Правила Конечного статуса:**
1.  **Флаг `IsFinal`**: В таблице `Statuses` должно быть поле `bool IsFinal`.
2.  **Read-Only**: Если `Order.Status.IsFinal == true`, система должна блокировать любые транзакции, кроме специальных (например, "Реопен" или "Корректировка").
3.  **Финансовое закрытие**: При переходе в `IsFinal` система должна убедиться, что дебет сходится с кредитом (оплата получена, товар отгружен).

### 5. Пайплайн Архивации (Archiving Pipeline)

Заказы, которые находятся в "Конечном статусе" долгое время, начинают тормозить систему. Их нужно убирать.

Это не происходит по кнопке. Это автоматический процесс.

#### Алгоритм (Job):

1.  **Критерии выборки:**
    *   `Status.IsFinal == true`
    *   `UpdatedAt < (Now - 6 months)` (настраивается в конфиге тенанта).
    *   `Balance == 0` (нет долгов по заказу).

2.  **Процесс переноса (Move):**
    Мы не просто копируем таблицу `Orders`. Нам нужно скопировать весь граф: `Orders` -> `Transactions` -> `TransactionItems`.

    *Рекомендую использовать JSON-сериализацию для архива (Стратегия 2 из прошлого ответа).*

```csharp
public class ArchivingJob
{
    public async Task ArchiveTenantData(Guid tenantId)
    {
        var cutoffDate = DateTime.UtcNow.AddMonths(-6);

        // 1. Находим кандидатов (только ID)
        var idsToArchive = await _db.Orders
            .Where(o => o.TenantId == tenantId && o.Status.IsFinal && o.UpdatedAt < cutoffDate)
            .Select(o => o.Id)
            .Take(100) // Пачками
            .ToListAsync();

        foreach (var orderId in idsToArchive)
        {
            // 2. Загружаем ПОЛНОЕ дерево заказа
            var orderGraph = await _db.Orders
                .Include(o => o.Items)
                .Include(o => o.Transactions).ThenInclude(t => t.Items)
                .AsSplitQuery()
                .FirstAsync(o => o.Id == orderId);

            // 3. Сериализуем в "Холодный документ"
            var archiveBlob = new OrderArchiveBlob
            {
                Id = orderGraph.Id,
                TenantId = tenantId,
                FinalDate = orderGraph.UpdatedAt,
                SearchNumber = orderGraph.Number, // Чтобы можно было найти поиском
                FullDataJson = JsonSerializer.Serialize(orderGraph)
            };

            // 4. Транзакция переноса
            using var tran = _db.Database.BeginTransaction();
            
            _db.ArchivedOrders.Add(archiveBlob); // В таблицу архива
            _db.Orders.Remove(orderGraph);       // Удаляем из оперативной
            // Каскадное удаление (Cascade Delete) в БД само удалит Items и Transactions
            
            await _db.SaveChangesAsync();
            await tran.CommitAsync();
        }
    }
}
```

### Итоговая картина

1.  **Пользователь** инициирует Транзакцию через Конструктор (UI).
2.  **TransactionService** собирает `Pipeline`:
    *   `Validate` -> `Stock` -> `Commit` -> `Notify`.
3.  Если заказ достиг **Конечного статуса**, он "застывает".
4.  Спустя полгода **ArchivingJob** тихо забирает его из оперативных таблиц, пакует в JSON и кладет в таблицу Архива, чтобы база не тормозила, но историю можно было поднять.
