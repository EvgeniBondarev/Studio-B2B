Для твоего SaaS-проекта (учет заказов, транзакции, мульти-тенантность) стандартная модель "Admin/User" **не подойдет**.

Тебе нужна **Permission-Based Authorization (Авторизация на основе прав)**.

### 🧠 Философия: Права vs Роли

1.  **Права (Permissions):** Это атомарные действия, зашитые в код.
    *   Пример: `Orders.Create`, `Transactions.Approve`, `Reports.View`.
    *   *Они неизменны*, так как разработчик пишет `[Authorize("Orders.Create")]` над методом контроллера.
2.  **Роли (Roles):** Это контейнеры для прав, хранящиеся в базе данных.
    *   Пример: "Менеджер", "Кладовщик", "Бухгалтер".
    *   *Они динамические*. Клиент сам создает роль "Старший кладовщик" и галочками набирает ей права.

### 1. Структура Данных (Tenant DB)

Так как у нас **изолированная база на каждого клиента**, мы используем стандартный **ASP.NET Core Identity**, но настраиваем его правильно.

Таблицы в БД клиента:
1.  `AspNetUsers` — Пользователи.
2.  `AspNetRoles` — Роли (создаются клиентом).
3.  `AspNetRoleClaims` — Связь Роли и Прав (Permissions).

> **Почему RoleClaims?** Потому что в Identity таблица `RoleClaims` идеально подходит для хранения списка строк-прав (`ClaimType`: "Permission", `ClaimValue`: "Orders.Create").

### 2. Список Прав (В Коде)

Создаем статический класс, который служит "Словарем" всех возможных действий в системе. Это контракт между бэкендом и базой.

```csharp
// MySaaS.Application/Constants/Permissions.cs

public static class Permissions
{
    public static class Orders
    {
        public const string View = "Orders.View";
        public const string Create = "Orders.Create";
        public const string Edit = "Orders.Edit";
        public const string Delete = "Orders.Delete";
    }

    public static class Transactions
    {
        public const string View = "Transactions.View";
        public const string Execute = "Transactions.Execute"; // Проведение
        public const string Approve = "Transactions.Approve"; // Согласование
    }

    public static class Integrations
    {
        public const string OneCSync = "Integrations.OneC.Sync";
        public const string Configure = "Integrations.Configure";
    }

    // Метод для получения всех прав списком (для UI редактора ролей)
    public static List<string> GetAll()
    {
        // Рефлексией собираем все константы
        return typeof(Permissions)
            .GetNestedTypes()
            .SelectMany(c => c.GetFields(BindingFlags.Public | BindingFlags.Static | BindingFlags.FlattenHierarchy))
            .Select(f => f.GetValue(null).ToString())
            .ToList();
    }
}
```

### 3. Авторизация (Middleware & Handlers)

Нам нужно, чтобы при входе пользователя система посмотрела его Роли, достала оттуда Права и положила их в `User.Claims`.

#### А. Настройка Identity (Program.cs)

```csharp
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>()
    .AddEntityFrameworkStores<TenantDbContext>() // Важно: храним в базе Тенанта!
    .AddDefaultTokenProviders();
```

#### Б. Dynamic Policy Provider (Магия автоматизации) 🧙‍♂️

Вместо того чтобы писать 100 раз `options.AddPolicy("Orders.View", ...)` в `Program.cs`, мы напишем провайдер, который создает Политики на лету.

Если контроллер просит `[Authorize(Policy = "Orders.Create")]`, этот провайдер скажет: "Ок, проверь, есть ли у юзера клейм `Permission` со значением `Orders.Create`".

```csharp
// MySaaS.Infrastructure/Auth/PermissionPolicyProvider.cs

public class PermissionPolicyProvider : IAuthorizationPolicyProvider
{
    public DefaultAuthorizationPolicyProvider FallbackPolicyProvider { get; }

    public PermissionPolicyProvider(IOptions<AuthorizationOptions> options)
    {
        FallbackPolicyProvider = new DefaultAuthorizationPolicyProvider(options);
    }

    public Task<AuthorizationPolicy> GetPolicyAsync(string policyName)
    {
        // Если имя политики совпадает с одним из наших пермишенов
        // Создаем политику динамически
        return Task.FromResult(new AuthorizationPolicyBuilder()
            .AddAuthenticationSchemes(JwtBearerDefaults.AuthenticationScheme)
            .RequireClaim("Permission", policyName) // <--- Главная проверка
            .Build());
    }

    public Task<AuthorizationPolicy> GetDefaultPolicyAsync() => FallbackPolicyProvider.GetDefaultPolicyAsync();
    public Task<AuthorizationPolicy> GetFallbackPolicyAsync() => FallbackPolicyProvider.GetFallbackPolicyAsync();
}
```

**Регистрация в DI:**
```csharp
builder.Services.AddSingleton<IAuthorizationPolicyProvider, PermissionPolicyProvider>();
```

### 5. UI: Редактор Ролей (В админке клиента)

Это то, что видит администратор клиента (Директор).

1.  **Список Ролей:** Таблица `AspNetRoles`. Кнопка "Создать роль".
2.  **Редактирование Роли:**
    *   Название: "Менеджер по продажам".
    *   Дерево чекбоксов (группируем по классам констант):
        *   **Заказы**
            *   [x] Просмотр
            *   [x] Создание
            *   [ ] Удаление (Опасно!)
        *   **Транзакции**
            *   [x] Проведение
            *   [ ] Настройка 1С

**Сохранение (Бэкенд):**
Когда клиент сохраняет роль, мы обновляем таблицу `AspNetRoleClaims`.

```csharp
public async Task UpdateRolePermissions(string roleId, List<string> selectedPermissions)
{
    var role = await _roleManager.FindByIdAsync(roleId);
    
    // 1. Удаляем старые клеймы
    var currentClaims = await _roleManager.GetClaimsAsync(role);
    foreach (var claim in currentClaims)
    {
        if (claim.Type == "Permission")
            await _roleManager.RemoveClaimAsync(role, claim);
    }

    // 2. Добавляем новые
    foreach (var permission in selectedPermissions)
    {
        await _roleManager.AddClaimAsync(role, new Claim("Permission", permission));
    }
}
```

### 6. Супер-Админ (SaaS Owner)

Тебе (владельцу SaaS) нужно иметь доступ ко всем тенантам для поддержки, но ты не хочешь создавать себе учетку в каждой базе.

**Решение: Middleware Impersonation (или Master Key)**.

В `PermissionPolicyProvider` или кастомном `AuthorizationHandler` добавь логику:
*"Если у пользователя есть Claim `IsSaaSAdmin = true` (выданный MasterDB), то разрешать любые действия, игнорируя проверку прав."*

---

### 7. Особый случай: Доступ к данным (Row-Level Security)

RBAC защищает **действия** (Создать), но не защищает **данные** (Чьи заказы я вижу?).
*   Менеджер А должен видеть только свои заказы.
*   РОП должен видеть заказы всего отдела.

Это реализуется **не через роли**, а через **Data Filters** в Query Handler'ах.

```csharp
public async Task<List<OrderDto>> Handle(GetOrdersQuery query)
{
    var dbQuery = _db.Orders.AsQueryable();

    // Если нет права "Видеть всё", фильтруем по автору
    if (!currentUser.HasPermission(Permissions.Orders.ViewAll))
    {
        dbQuery = dbQuery.Where(x => x.CreatedById == currentUser.Id);
    }

    return await dbQuery.ToListAsync();
}
```

### Итоговое Резюме

1.  **Изоляция:** Используй таблицы Identity (`AspNetRoles`, `AspNetRoleClaims`) прямо в базе Тенанта.
2.  **Код:** Права (`Permissions`) — это константы в коде C#.
3.  **Связь:** Роль — это набор `RoleClaims` с типом "Permission".
4.  **Проверка:** `IAuthorizationPolicyProvider` автоматически превращает константы в политики ASP.NET.
5.  **UI:** Клиент сам ставит галочки, какие права давать какой роли.

Это **Enterprise-стандарт**. Он гибкий, производительный (клеймы лежат в куке/токене и не требуют запроса в БД на каждый чих) и безопасный.
